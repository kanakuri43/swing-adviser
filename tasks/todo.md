# バックテスト（最小限の検証ツール）

## 目的
`StrategyParameters` の仮値と候補の選び方（早期シグナルを残すか、地合い不一致を除くか、スコア閾値など）を、過去データの結果で判断できるようにする。主指標は平均R（期待値）で、勝率は補助指標。設計上の制約は CLAUDE.md「バックテスト」節を正とする。

## 方針（要約）
- 新規コンソールプロジェクト `tools/SwingAdviser.Backtest`（Domain・Infrastructure を参照）。アプリ本体・本番DB・UIは変更しない。
- 判定は Domain の `CandidateScanner` / `HoldingRiskEvaluator` をそのまま呼ぶ。専用ロジックを複製しない。
- 日足は Yahoo から約5年分を取得し、gitignore したローカルキャッシュに保存する。2回目以降はキャッシュを使う。
- 評価日 t では t 以前の `BarsToFetch` 本だけを渡す。t+1 始値で建て、毎日の終値で判定し、翌営業日始値で決済する。
- 出力はトレード明細CSVと切り口別の集計（コンソール＋CSV）。テーブル・マイグレーションは追加しない。

## 実装項目

### 1. プロジェクト基盤
- [x] `tools/SwingAdviser.Backtest`（console, net10.0）を作成し、`SwingAdviser.slnx` に追加する（`dotnet build` の対象に含める）
- [x] 設定読み込み: 既定はアプリの `appsettings.json` の `StrategyParameters` / `MarketData` / `LiquidityFilter`。`--settings <path>` で別ファイルを上書きできるようにする
- [x] 引数: `fetch`（データ取得）/ `run`（シミュレーション）の2コマンド。期間（`--from` / `--to`）と前半・後半の分割日（`--split`）を指定できる
- [x] `.gitignore` にキャッシュ・出力ディレクトリを追加する

### 2. データ取得・キャッシュ（`fetch`）
- [x] `JpxListedIssuesClient` で銘柄一覧を取得する（現在の上場銘柄。生存バイアスはCLAUDE.md記載の通り許容）
- [x] `YahooFinanceClient.FetchAsync(code, since)` で各銘柄と 1306 の約5年分を取得し、銘柄ごとにCSVでキャッシュする（既存キャッシュがあればスキップ。`--refresh` で再取得）
- [x] 1銘柄の取得失敗は理由をログに出してスキップし、全体を止めない。1306 の取得失敗だけは中断する
- [x] Yahoo の日足は大半が分割調整済みだが、実データで不備を確認したため `BarCleaner` で取得時に補正する（任天堂7974は調整済み／7946・5537は分割イベントがあるのに過去が未調整／1306・9204はイベント欠落で段差／8303は出来高0の異常価格バー）。分割イベントの前後で終値の段差が分割比に近ければ未調整とみなして調整、イベントが無い3倍超の段差は比率を推定して調整、出来高0で3倍超乖離したバーは除外。テスト済み

### 3. シミュレーション本体（`run`）
- [x] 取引日カレンダーは 1306 の日足の日付列とする
- [x] 各評価日 t・各銘柄について:
  - [ ] その銘柄に t のバーが無ければスキップする（売買停止など）
  - [ ] t 以前の直近20営業日で `LiquidityFilter.IsEligible` を判定し、不適格ならスキップする
  - [ ] t 以前の直近 `BarsToFetch` 本と 1306 の同期間を `CandidateScanner.Evaluate` に渡す（`MinimumRequiredBars` 未満ならスキップ）
- [x] 建玉: 候補が出たら t+1 の始値で建てる。損切は `建値 − 符号×倍率×ATR14(t)` で、本番の `ExecutionEntryService` と同じ式にする。`Position.Open` で Domain の `Position` を作る（Short は `isMargin: true`）
- [x] 同一銘柄・同一方向でシミュレーション中のトレードがあれば新規に建てない
- [x] 保有中: 毎日 t の終値時点のバー列で `HoldingRiskEvaluator.Evaluate` を呼ぶ
  - 損切は逆指値モデル（決定事項1）。建玉日を含む毎日、始値の決済処理のあとにザラ場の高安でライン到達を判定し、ラインの価格（ギャップ時は始値）で約定する
  - TimeStop / Exit（および終値ベースで StopLoss と判定された場合）→ t+1 始値で残り全量を決済
  - TakeProfit → t+1 始値で残数量の `PartialTakeProfitRatio` を決済（`AddCloseExecution`）。2回目以降は Domain 側の「一部利確済み」判定に従う
- [x] 途中でバーが途切れたら（上場廃止など）最後の終値で決済し、理由「データ終了」とする。期間末で未決済のトレードも同様に「期間末」とする
- [x] 銘柄単位で並列化する（銘柄間に依存が無いため）。進捗はコンソールに出す

### 4. 出力・集計
- [x] トレード明細CSV（1行=1トレード）: 銘柄、方向、シグナル日、建玉日・建値、決済日・加重平均決済値、損切ライン、R倍率の結果、最大含み益/最大含み損（MFE/MAE、R単位）、保有営業日数、決済理由、および候補時点の属性（スコア、信頼度、確定/早期、クロス経過日数、地合い一致、出来高倍率、過熱度、各スコア内訳）
- [x] 集計（コンソール表＋CSV）: 件数、勝率、平均R、中央値R、プロフィットファクター、累積Rの最大ドローダウン（決済日順）
- [x] 集計の切り口: 全体 / 方向 / 確定と早期 / 地合い一致と不一致 / 信頼度 / スコア帯（10点刻み）/ 決済理由 / 年 / 前半と後半

### 5. テスト（`tests/SwingAdviser.Tests` に追加。合成した日足を使う）
- [x] 未来データ混入なし: 評価日 t より後のバーを書き換えても、t のシグナル・建玉判断が変わらない
- [x] 約定タイミング: 建玉は t+1 始値、決済は判定日の翌営業日始値で行われる（シグナル日の終値で約定しない）
- [x] 損切ラインが本番と同じ式で、保有中に上書きされない
- [x] 一部利確 → 残りの Exit の順で、数量とR合計が正しい
- [x] 重複建玉の抑止、データ途切れ・期間末の強制決済
- [x] 集計指標（勝率・平均R・PF・最大DD）を手計算できる小さなトレード列で検証する

### 6. 検証・初回実行
- [x] `dotnet build` / `dotnet test` が通る（217件合格、うちバックテスト関連21件）
- [x] `fetch` → `run` を現行の `appsettings.json` で実行し、ベースラインの結果を下の「レビュー」に記録した
- [x] 結果を見て変更案をまとめた（下の「レビュー」）。`appsettings.json` への反映は未実施（前半で決めて後半で効くことを確認してから、別タスクで相談する）

## 決定事項
1. 損切の約定モデル: 証券会社の逆指値を使う運用のため、ザラ場でライン到達なら「ラインの価格」、始値がラインを超えたギャップなら「始値」で約定とする（建玉日当日の値動きも対象）。
2. 期間: 約5年分を取得し、評価は約4年分。前半・後半の分割日の既定は評価期間の中間点。
3. Short: 全銘柄を対象にする（空売りできない銘柄が含まれる点は結果を割り引いて読む）。

## レビュー
### 実装
- `tools/SwingAdviser.Backtest`（`fetch` / `run`）。本体・本番DB・UIは変更なし。アプリ側のコードは `CandidateScanner` / `HoldingRiskEvaluator` / `Position` / `LiquidityFilter` / `YahooFinanceClient` / `JpxListedIssuesClient` を再利用しただけで、判定ロジックの複製はない。
- 使い方（リポジトリ直下で）: `dotnet run --project tools/SwingAdviser.Backtest -c Release -- fetch`（約13分、キャッシュは `backtest-cache/`）、`... -- run --out backtest-output/<名前>`（約1.5分）。設定を変えて比べるときは `--settings <別のjson>` と `--out` を変える。
- 実データで Yahoo の日足に不備があり（分割の未調整・イベント欠落・出来高0の異常価格）、最初の実行では平均Rが数万になった。`BarCleaner` を追加して補正し、再取得して解消。

### 読み取れること（仮説であり、まだ設定は変えていない）
1. **現行の仮値ではほぼ優位性が出ていない**（全体 +0.016R）。Long だけが小さくプラス（+0.10R）で、これは生存バイアス（上場廃止銘柄が無い）を割り引くとさらに小さくなる可能性が高い。
2. **Short は前半・後半ともにマイナス**（−0.11R、地合い一致では −0.23R）。空売り不可銘柄が含まれる点を割り引いても、現行条件のままでは Short 候補を使う根拠が無い。
3. **スコア・信頼度が成績を予測していない**（スコア帯ごとの平均Rに単調な関係が無く、High と Low が同程度）。配点（特に地合い15点）の見直し候補。地合い「一致」の方が成績が悪い。
4. **早期シグナルは確定より少し劣る程度**で、致命的に悪くはない。候補数は早期が約8割を占める。
5. 損切に当たるのは34%（平均 −1.05R、ギャップ分）。損切に当たらず20営業日保有できたものは平均 +0.54R。損切幅（Long 3.0ATR）と利確・Exit の設計が成績の大部分を決めている可能性が高い。次に検証する価値が高い。
6. 最大ドローダウンは全候補を独立に積み上げた累積Rなので、実運用の資金推移とは別物（比較用の指標としてのみ使う）。

### 設定変更案の比較（1要素ずつ変更、14案。境 2024-09-03、`backtest-output/variants/*.json`）
全体の平均R（前半 / 後半）。ベースラインは +0.010 / +0.021。
- 損切倍率（Long 2.0/2.5/4.0、Short 2.0/3.5）、TimeStop（10/15/30日）、利確（1.0R/2.5R）、MACDクロス日数1、過熱閾値（1.0/3.0）はいずれも **±0.02R 程度の差**で、前半と後半で優劣が一致しない（例: 早期シグナル無効は前半 +0.036 → 後半 −0.008）。日別平均Rの標準誤差だけでも約0.011あり（同日の候補は相関するので実際はもっと大きい）、**差はノイズの範囲**。→ どの変更も採用しない。
- 唯一どの案でも前半・後半とも一貫したのは **Short が負け、Long が勝つ**こと（ベースラインで Long +0.067/+0.131、Short −0.081/−0.141）。損切倍率や保有日数を変えても Short は黒字化しない。
- Long の内訳でも、地合い一致/不一致、出来高倍率（≥1.5 と <1.0）、過熱度（<0.5ATR と ≥1.5ATR）で成績がほぼ変わらない。**現行のスコア配点は成績を区別できていない**（優位性があるとすれば、候補条件そのもの＝Long のMACD反転＋EMA100上昇トレンド）。
- 注意: Long は生存バイアス、Short は貸株料・逆日歩・空売り不可銘柄の未考慮で、実際の Short はさらに悪い方向にずれる。

### 結論（設定値は未変更）
採用候補は「Short 候補を使わない/目立たなくする」の1点のみ。仕様（CLAUDE.md の Long/Short 対称）に関わるためユーザーの判断待ち。スコア配点は成績を区別できていないので、今は「High だから良い」と読まない。

### Short 候補の無効化（実施済み）
- `Gates.ShortCandidatesEnabled`（既定 false）を追加し、`CandidateScanner` が false なら Short を評価しない。候補一覧・AI自動評価・日次更新は Scanner の結果をそのまま使うため、Short は一切出ない。保有中 Short の再評価（`HoldingRiskEvaluator`）・約定入力は変更なし。
- バックテストも同じ設定を読むため、既定では Long のみになる。Short を含めて比べるときは設定ファイルで `ShortCandidatesEnabled: true` にする。
- テスト: 無効時に Short が出ず Long は不変／有効時は従来どおり出る／appsettings の既定が false。全218件合格。
